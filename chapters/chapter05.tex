\section{Metodología}

El desarrollo del prototipo sigue un enfoque \textbf{iterativo e incremental}: la funcionalidad se construye en hitos sucesivos, cada uno con valor demostrable, priorizando primero la base transversal (autenticación, persistencia y ciclo de vida del envío) y avanzando luego hacia los componentes diferenciales (asignación inteligente, clasificación por visión computacional y cálculo de impacto ambiental). Este orden permite validar de forma temprana las decisiones de diseño fundamentadas en los antecedentes y ajustar el alcance según los resultados.

El trabajo se apoya en un conjunto de prácticas de ingeniería: control de versiones con Git y GitHub, empaquetado reproducible mediante contenedores, configuración externalizada por entorno y pruebas automatizadas sobre los módulos críticos. La construcción del conjunto de datos para el clasificador se inicia en paralelo desde las primeras etapas, por ser la tarea que no puede acelerarse con código.

\section{Arquitectura de la solución}

La solución adopta el patrón de \textbf{monolito modular orientado a dominio}: una única aplicación de servidor organizada en módulos autocontenidos, cada uno responsable de un dominio del negocio. Se descarta una arquitectura de microservicios porque su complejidad operativa (comunicación de red entre servicios, observabilidad distribuida y consistencia eventual) no se justifica en un prototipo de estas dimensiones; la modularización interna preserva, no obstante, límites claros que habilitarían la extracción de un servicio en el futuro si la escala lo requiriera.

La arquitectura se describe siguiendo el modelo \textbf{C4}, de mayor a menor nivel de abstracción.

\begin{itemize}[leftmargin=2em]
    \item \textbf{Contexto.} El sistema atiende a cinco tipos de actor (cliente particular, transportista, PyME fletera, PyME comercio y administrador) a través de dos frentes —una aplicación móvil para clientes y transportistas y un panel web para PyMEs y administración— sobre un único backend. Sus dependencias externas son mínimas y reemplazables: un servicio de ruteo (con alternativa de cálculo propia), un servicio de mapas y geocodificación, y la persistencia de datos e imágenes.
    \item \textbf{Contenedores.} Las unidades desplegables por separado son: la aplicación móvil, el panel web, la API REST, la base de datos y el almacenamiento de las imágenes de los paquetes. Las aplicaciones cliente se comunican con la API sobre HTTPS con autenticación por token; la API concentra toda la lógica de negocio y el acceso a datos.
    \item \textbf{Componentes.} Dentro de la API, cada módulo de dominio respeta una separación estricta en cuatro capas —enrutamiento (HTTP y validación), servicio (lógica de negocio), repositorio (acceso a datos) y esquemas—, con una regla de dependencia unidireccional. Los módulos implementados abarcan autenticación, usuarios, transportistas, envíos, trayectos, asignación, visión, seguimiento, impacto ambiental, organizaciones y administración.
\end{itemize}

\subsection{Arquitectura de red e infraestructura}

El entorno de ejecución actual es local y está contenedorizado: la base de datos PostgreSQL, la API y el panel web se levantan de forma reproducible mediante una definición única de servicios, lo que garantiza que todo integrante del equipo trabaje sobre la misma configuración. La aplicación móvil se ejecuta sobre el entorno de desarrollo de su plataforma y consume la API por red local.

Sobre los protocolos, la comunicación entre las aplicaciones cliente y el servidor se realiza mediante una interfaz REST sobre HTTP, con contenidos en formato JSON y verbos que respetan la semántica del protocolo. La autenticación es sin estado y se resuelve con tokens firmados que el cliente adjunta en la cabecera de autorización de cada solicitud, junto con un token de refresco de mayor vigencia que permite renovar la sesión sin reingresar credenciales. La comunicación con el servicio externo de ruteo se realiza también sobre HTTP; ante su indisponibilidad, el sistema degrada de forma automática a una estimación de distancias propia (RNF-AVL-01). En un escenario publicado, la totalidad del tráfico entre cliente y servidor se transporta sobre HTTPS.

La topología de destino se diseñó bajo la restricción de presupuesto acotado (RNF-INF-01), sobre servicios gestionados: la API dentro de un contenedor sobre una plataforma como servicio, una base de datos PostgreSQL gestionada y el panel web publicado como sitio estático. El dimensionamiento de los planes contratados se ajustará a lo necesario para sostener la disponibilidad del sistema durante el desarrollo y la defensa. La definición de infraestructura correspondiente está escrita y versionada en el repositorio, pero la publicación efectiva del sistema queda pendiente para la etapa final del proyecto. Esta elección preserva la portabilidad (RNF-INF-02): migrar de proveedor implica cambiar dónde se ejecuta el mismo contenedor, no el código de la aplicación.

Los atributos geográficos (orígenes, destinos y trazas) se modelan como pares de coordenadas, y las consultas de proximidad del \emph{matching} se resuelven por cálculo de distancia sobre esas coordenadas, con un factor de corrección que aproxima el recorrido real por calles frente a la distancia en línea recta. La adopción de tipos e índices espaciales nativos del motor queda planteada como optimización posterior, cuando el volumen de datos lo justifique. El ciclo de vida del envío se gobierna mediante una máquina de estados (pendiente $\rightarrow$ asignado $\rightarrow$ arribo al retiro $\rightarrow$ en tránsito $\rightarrow$ entregado, con transición a cancelado), donde cada cambio válido se registra como un evento de auditoría con marca temporal y ubicación (RF-SHP-05).

\section{Validación del sistema}

La validación combina pruebas automatizadas del software y evaluación cuantitativa del modelo de inteligencia artificial.

En el backend, la verificación se apoya en un conjunto de pruebas automatizadas organizadas por módulo, que cubren autenticación, envíos, asignación, trayectos, visión, seguimiento, impacto ambiental, organizaciones y administración, junto con pruebas de los flujos de integración de punta a punta (RNF-MNT-02). El diseño favorece esta verificación: los cálculos centrales del \emph{matching} y del CO\textsubscript{2} se implementan como funciones puras y determinísticas, lo que permite comprobar de forma directa la tabla de compatibilidad vehículo-carga, los filtros duros (descarte de la modalidad colaborativa para cargas voluminosas, de la movilidad a pie o en bicicleta en trayectos largos y de los desvíos por encima del máximo admitido), el ordenamiento por proximidad y el cálculo del ahorro de emisiones con coordenadas reales del AMBA.

El modelo de clasificación de carga se evalúa exclusivamente sobre el conjunto de prueba, separado de forma estratificada y reservado hasta la instancia de evaluación. El procedimiento está implementado y automatizado: reporta la exactitud global, la precisión, la exhaustividad y la medida F por categoría, y la matriz de confusión, prestando atención a las confusiones entre categorías adyacentes. Complementariamente, ejecuta un análisis de sesgos que agrupa el conjunto de prueba según las condiciones de captura —iluminación, ángulo y fondo— y según la presencia de un objeto de referencia, calculando la exactitud por grupo para detectar y documentar las condiciones en las que el desempeño se degrada (RNF-UADE-01). Este análisis alimenta tanto las mitigaciones del modelo como las recomendaciones de uso en la interfaz.

A la fecha de esta entrega se entrenó una primera versión del clasificador mediante aprendizaje por transferencia sobre una red convolucional preentrenada, con un conjunto de datos de 1.079 imágenes repartidas de forma estratificada entre entrenamiento, validación y prueba. Esta versión constituye la línea base sobre la que se mide la mejora del modelo; la ampliación del conjunto de datos y la evaluación definitiva sobre el conjunto de prueba forman parte del trabajo previsto para la etapa final.
