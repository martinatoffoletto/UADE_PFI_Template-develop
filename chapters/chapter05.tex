\section{Metodología}

El desarrollo del prototipo sigue un enfoque \textbf{iterativo e incremental}: la funcionalidad se construye en hitos sucesivos, cada uno con valor demostrable, priorizando primero la base transversal (autenticación, persistencia y ciclo de vida del envío) y avanzando luego hacia los componentes diferenciales (asignación inteligente, clasificación por visión computacional y cálculo de impacto ambiental). Este orden permite validar de forma temprana las decisiones de diseño fundamentadas en los antecedentes y ajustar el alcance según los resultados.

El trabajo se apoya en un conjunto de prácticas de ingeniería: control de versiones con Git y GitHub, empaquetado reproducible mediante contenedores, configuración externalizada por entorno y pruebas automatizadas sobre los módulos críticos. La construcción del conjunto de datos para el clasificador se inicia en paralelo desde las primeras etapas, por ser la tarea que no puede acelerarse con código.

\section{Arquitectura de la solución}

La solución adopta el patrón de \textbf{monolito modular orientado a dominio}: una única aplicación de servidor organizada en módulos autocontenidos, cada uno responsable de un dominio del negocio. Se descarta una arquitectura de microservicios porque su complejidad operativa (comunicación de red entre servicios, observabilidad distribuida y consistencia eventual) no se justifica en un prototipo de estas dimensiones; la modularización interna preserva, no obstante, límites claros que habilitarían la extracción de un servicio en el futuro si la escala lo requiriera.

La arquitectura se describe siguiendo el modelo \textbf{C4}, de mayor a menor nivel de abstracción.

\begin{itemize}[leftmargin=2em]
    \item \textbf{Contexto.} El sistema atiende a los cuatro actores identificados en el Capítulo~\ref{cap:requerimientos} —remitente, transportista, PyME u organización y administrador—, con la salvedad de que la organización se distingue internamente en dos variantes según su vínculo con la plataforma: la que opera una flota de transportistas y la que es comercio y programa sus propios envíos. El acceso ocurre a través de dos frentes —una aplicación móvil para clientes y transportistas y un panel web para PyMEs y administración— sobre un único backend. Sus dependencias externas son mínimas y reemplazables: un servicio de ruteo (con alternativa de cálculo propia), un servicio de mapas y geocodificación, y la persistencia de datos e imágenes.
    \item \textbf{Contenedores.} Las unidades desplegables por separado son: la aplicación móvil, el panel web, la API REST, la base de datos y el almacenamiento de las imágenes de los paquetes. Las aplicaciones cliente se comunican con la API sobre HTTPS con autenticación por token; la API concentra toda la lógica de negocio y el acceso a datos.
    \item \textbf{Componentes.} Dentro de la API, cada módulo de dominio respeta una separación estricta en cuatro capas —enrutamiento (HTTP y validación), servicio (lógica de negocio), repositorio (acceso a datos) y esquemas—, con una regla de dependencia unidireccional. Los módulos implementados abarcan autenticación, usuarios, transportistas, envíos, trayectos, asignación, visión, seguimiento, impacto ambiental, organizaciones y administración.
\end{itemize}

Conviene destacar el momento en que se calcula el impacto ambiental. El ahorro de CO\textsubscript{2} aparece dos veces y con dos significados distintos: en la cotización es una \emph{estimación} optimista, calculada sobre el viaje dedicado equivalente porque todavía no se conoce qué transportista tomará el envío; el valor definitivo se calcula y persiste recién cuando un transportista acepta, ya que solo entonces se conocen su trayecto publicado y su tipo de vehículo, que son los datos que permiten medir el desvío real frente al viaje que esa persona ya iba a hacer. La entrega, en cambio, no recalcula emisiones: únicamente libera el pago retenido.

\subsection{Arquitectura de red e infraestructura}

El entorno de ejecución actual es local y está contenedorizado: la base de datos PostgreSQL, la API y el panel web se levantan de forma reproducible mediante una definición única de servicios, lo que garantiza que todo integrante del equipo trabaje sobre la misma configuración. La aplicación móvil se ejecuta sobre el entorno de desarrollo de su plataforma y consume la API por red local.

Sobre los protocolos, la comunicación entre las aplicaciones cliente y el servidor se realiza mediante una interfaz REST sobre HTTP, con contenidos en formato JSON y verbos que respetan la semántica del protocolo. La autenticación es sin estado y se resuelve con tokens firmados que el cliente adjunta en la cabecera de autorización de cada solicitud, junto con un token de refresco de mayor vigencia que permite renovar la sesión sin reingresar credenciales. La comunicación con el servicio externo de ruteo se realiza también sobre HTTP; ante su indisponibilidad, el sistema degrada de forma automática a una estimación de distancias propia (RNF-AVL-01). En un escenario publicado, la totalidad del tráfico entre cliente y servidor se transporta sobre HTTPS.

La topología de destino se diseñó bajo la restricción de presupuesto acotado (RNF-INF-01), sobre servicios gestionados: la API dentro de un contenedor sobre una plataforma como servicio, una base de datos PostgreSQL gestionada y el panel web publicado como sitio estático. El dimensionamiento de los planes contratados se ajustará a lo necesario para sostener la disponibilidad del sistema durante el desarrollo y la defensa. La definición de infraestructura correspondiente está escrita y versionada en el repositorio, pero la publicación efectiva del sistema queda pendiente para la etapa final del proyecto. Esta elección preserva la portabilidad (RNF-INF-02): migrar de proveedor implica cambiar dónde se ejecuta el mismo contenedor, no el código de la aplicación.

\section{Tecnologías utilizadas}

La selección de tecnologías responde a los requerimientos no funcionales y a las decisiones de diseño fundamentadas en los antecedentes. Se expone primero la elección de los lenguajes de programación, que condiciona al resto de las decisiones, y luego el \emph{stack} completo por capa.

\subsection{Elección de los lenguajes de programación}

El sistema se escribe en dos lenguajes: \textbf{Python} (versión 3.11 o superior) en el servidor y en el canal de entrenamiento del modelo, y \textbf{TypeScript} en los dos frentes cliente.

La elección de Python en el backend no responde a una preferencia general por el lenguaje, sino a una restricción concreta del proyecto: el clasificador de carga por visión computacional es uno de los tres componentes diferenciales de la propuesta, y las bibliotecas maduras de aprendizaje profundo —TensorFlow y Keras, empleadas para el aprendizaje por transferencia— pertenecen al ecosistema de Python. Escribir el servidor en el mismo lenguaje permite que la inferencia se ejecute dentro del proceso que atiende la API, cargando el modelo entrenado en memoria al iniciar. La alternativa —un backend en otro lenguaje— obligaría a exponer el modelo como un servicio independiente, lo que introduciría una segunda unidad desplegable, un protocolo de comunicación adicional entre ambos y un punto de falla más. Esa consecuencia contradice tanto la decisión de arquitectura de monolito modular como la restricción de presupuesto acotado (RNF-INF-01). A esto se suman dos propiedades del lenguaje que el diseño aprovecha de forma directa: el modelo de concurrencia asíncrono, adecuado para una carga dominada por operaciones de entrada/salida (consultas a la base de datos y llamadas al servicio de ruteo) antes que por cómputo intensivo; y las anotaciones de tipo, que el \emph{framework} web utiliza para validar automáticamente los datos de entrada y generar la documentación de la API (RNF-SEC-04, RNF-MNT-03).

Del lado del cliente se optó por TypeScript sobre JavaScript por su verificación estática de tipos. La razón es específica del proyecto: la aplicación móvil y el panel web consumen la misma API, que continúa evolucionando durante el desarrollo, y el tipado permite que un cambio en el contrato de un \emph{endpoint} se manifieste como un error de compilación y no como una falla en tiempo de ejecución detectada por el usuario. Emplear un único lenguaje en ambos frentes, sobre una misma biblioteca de interfaz, permite además declarar una sola vez los tipos de las respuestas de la API y reutilizarlos en los dos clientes, evitando definiciones duplicadas que tienden a divergir.

Se evaluaron y descartaron dos alternativas. La primera, un backend sobre una plataforma de tipado estático como Java o C\#: ofrece mayor robustez en sistemas de gran escala, pero obliga a la separación del componente de inteligencia artificial ya descrita, sin un beneficio proporcional en un prototipo de este tamaño. La segunda, unificar todo el sistema en TypeScript ejecutando también el servidor sobre Node.js: resulta atractiva porque reduciría el proyecto a un solo lenguaje, pero reintroduce exactamente el mismo problema, dado que el ecosistema de aprendizaje profundo en ese entorno es sensiblemente menos maduro y volvería a exigir un servicio en Python para el modelo. En el cliente se descartó el desarrollo nativo separado para cada plataforma móvil, que ofrece mejor rendimiento pero implica mantener dos bases de código independientes, esfuerzo inviable para un equipo de dos personas dentro del cronograma del proyecto.

\section{Diseño de la interfaz}

Los criterios que guían el diseño responden a los requerimientos no funcionales de usabilidad (RNF-UX-01) y a los hallazgos de la investigación de usuarios: transparencia del precio antes de confirmar, visibilidad del desvío y de la ganancia para el transportista, y presencia del dato ambiental sin que interfiera con la decisión principal.

\section{Validación del sistema}

La validación combina pruebas automatizadas del software y evaluación cuantitativa del modelo de inteligencia artificial.

En el backend, la verificación se apoya en un conjunto de pruebas automatizadas organizadas por módulo, que cubren autenticación, envíos, asignación, trayectos, visión, seguimiento, impacto ambiental, organizaciones y administración, junto con pruebas de los flujos de integración de punta a punta (RNF-MNT-02). El diseño favorece esta verificación: los cálculos centrales del \emph{matching} y del CO\textsubscript{2} se implementan como funciones puras y determinísticas, lo que permite comprobar de forma directa la tabla de compatibilidad vehículo-carga, los filtros duros (descarte de la modalidad colaborativa para cargas voluminosas, de la movilidad a pie o en bicicleta en trayectos largos y de los desvíos por encima del máximo admitido), el ordenamiento por proximidad y el cálculo del ahorro de emisiones con coordenadas reales del AMBA.

El modelo de clasificación de carga se evalúa exclusivamente sobre el conjunto de prueba, separado de forma estratificada y reservado hasta la instancia de evaluación. El procedimiento está implementado y automatizado: reporta la exactitud global, la precisión, la exhaustividad y la medida F por categoría, y la matriz de confusión, prestando atención a las confusiones entre categorías adyacentes. Sobre esa evaluación se verifican las dos condiciones fijadas en el objetivo específico correspondiente del Capítulo~\ref{cap:introduccion}: una exactitud no inferior al 70~\% y una distribución del error concentrada en categorías contiguas, que es la que la corrección manual del remitente absorbe con menor fricción. Complementariamente, ejecuta un análisis de sesgos que agrupa el conjunto de prueba según las condiciones de captura —iluminación, ángulo y fondo— y según la presencia de un objeto de referencia, calculando la exactitud por grupo para detectar y documentar las condiciones en las que el desempeño se degrada (RNF-UADE-01). Este análisis alimenta tanto las mitigaciones del modelo como las recomendaciones de uso en la interfaz.

A la fecha de esta entrega se entrenó una primera versión del clasificador mediante aprendizaje por transferencia sobre una red convolucional preentrenada, con un conjunto de datos de 1.079 imágenes repartidas de forma estratificada entre entrenamiento, validación y prueba. Esta versión constituye la línea base sobre la que se mide la mejora del modelo; la ampliación del conjunto de datos y la evaluación definitiva sobre el conjunto de prueba forman parte del trabajo previsto para la etapa final.
